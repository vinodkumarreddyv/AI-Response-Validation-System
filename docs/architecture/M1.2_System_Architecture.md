# M1.2 --- System Architecture

## 1. Overview

The AI Response Validation System is designed as a modular evaluation
platform for assessing AI-generated responses against reference answers
and retrieved knowledge.

The architecture separates user interaction, API processing, knowledge
retrieval, evaluation agents, scoring, verdict generation, and result
presentation.

The main evaluation flow is:

``` text
User
  |
  v
Evaluation Input / User Interface
  |
  v
Backend / API Layer
  |
  v
Evaluation Input Processing
  |
  +-----------------------------+
  |                             |
  v                             v
Reference Answer          Reference Knowledge Base
                                |
                                v
                         Embedding Generation
                                |
                                v
                         Vector Search / FAISS
                                |
                                v
                         Retrieved Evidence
                                |
                                +-------------+
                                              |
                                              v
                                  Evaluation Orchestrator
                                              |
                    +-------------------------+-------------------------+
                    |                         |                         |
                    v                         v                         v
             Relevance Judge          Accuracy Judge          Hallucination
                 Agent                    Agent              Detection Agent
                    |                         |                         |
                    +-------------------------+-------------------------+
                                              |
                                              v
                                   Completeness Judge Agent
                                              |
                                              v
                                        Verdict Agent
                                              |
                                              v
                                  Evaluation Scoring Result
                                              |
                                              v
                                  Results / Evaluation Dashboard
```

------------------------------------------------------------------------

## 2. Architectural Goals

The architecture is designed around the following goals:

-   Modular evaluation components.
-   Clear separation of responsibilities.
-   Evidence-grounded response evaluation.
-   Reusable knowledge-base retrieval.
-   Independent evaluation dimensions.
-   Transparent scoring.
-   Structured evaluation results.
-   Easy extension for future milestones.
-   Support for both reference-based and retrieval-based evaluation.
-   Ability to introduce LLM-based judge agents without redesigning the
    complete system.

## 4. Evaluation Input / User Interface

The Evaluation Input Interface is the entry point for an evaluation
request.

### Primary inputs

-   Question
-   AI-generated response

### Optional inputs

-   Reference answer
-   Source document
-   Reference material

The interface validates the required fields before sending an evaluation
request to the backend.

Example:

``` text
Question:
What is the capital of France?

AI Response:
Paris

Reference Answer:
Paris

Retrieved Evidence:
Paris is the capital of France.
```

The interface displays the final evaluation result after processing.

------------------------------------------------------------------------

## 5. Backend / API Layer

The Backend / API Layer provides communication between the frontend and
evaluation services.

Responsibilities include:

-   Receive evaluation submissions.
-   Validate request structure.
-   Forward inputs to the evaluation pipeline.
-   Trigger retrieval.
-   Trigger evaluation.
-   Return structured results.
-   Handle errors.
-   Provide a stable API boundary between frontend and backend.

The project uses Python and FastAPI for the backend/API layer.

------------------------------------------------------------------------

## 6. Evaluation Submission and Input Processing

The input processing module converts the user submission into a
standardized evaluation request.

A standardized request can contain:

``` text
evaluation_id
question
ai_response
reference_answer
source_document
reference_material
```

The module performs validation such as:

-   Question must not be empty.
-   AI response must not be empty.
-   Optional fields may be absent.
-   Input text must be valid.
-   Invalid requests should return an appropriate error.

The processed request is passed to the evaluation orchestrator.

## 8. Benchmark Dataset Ingestion Module

The Benchmark Dataset Ingestion Module collects benchmark datasets and
stores the raw data.

Current datasets:

``` text
TruthfulQA
SQuAD
```

The raw datasets are stored under:

``` text
data/raw/
```

The ingestion implementation uses the Hugging Face Datasets library.

The current ingestion results are:

``` text

SQuAD validation:  10,570 records
```

------------------------------------------------------------------------

## 9. Data Cleaning and Chunking Pipeline

The preprocessing pipeline standardizes the ingested benchmark data.

The current cleaning operations include:

-   Whitespace normalization.
-   Empty-record filtering.
-   Field standardization.
-   Record ID generation.
-   Extraction of question, answer, context, title, and source fields.

Processed data is stored under:

``` text
data/processed/
```

The chunking stage divides source text into smaller units for semantic
retrieval.

Current configuration:

``` text
Chunk size: 500 words
Overlap: 50 words
```

Generated chunks are stored under:

``` text
data/chunks/
```

------------------------------------------------------------------------

## 10. Embedding Generation Module

The Embedding Generation Module converts text chunks into numerical
vector representations.

The selected model is:

``` text
all-MiniLM-L6-v2
```

Embedding dimension:

``` text
384
```

Embeddings are normalized before vector indexing.

The generated embedding files are stored under:

``` text
data/embeddings/
```

The same embedding model is used for query embedding during retrieval.

------------------------------------------------------------------------

## 11. Vector Database / Semantic Search

The system uses FAISS for semantic vector search.

FAISS stores the knowledge-base embeddings and retrieves vectors that
are closest to a submitted query.

Current Milestone 1 index:

``` text
Total vectors: 99,024
Dimension: 384
```

The vector store contains:

``` text
knowledge_base.index
chunks.json
metadata.json
```

The vector store enables semantic retrieval rather than relying only on
exact keyword matching.

------------------------------------------------------------------------

## 12. RAG Retrieval Pipeline

The retrieval pipeline provides evidence for response evaluation.

The flow is:

``` text
Submitted Question
       |
       v
Query Embedding
       |
       v
FAISS Search
       |
       v
Top Relevant Chunks
       |
       v
Evidence Ranking
       |
       v
Retrieved Evidence
```

The retrieved evidence is passed to the evaluation orchestrator.

The retrieval system can provide signals such as:

-   FAISS distance
-   Semantic similarity
-   Keyword overlap
-   Phrase score
-   Direct fact score
-   Relevance score
-   Exact match

------------------------------------------------------------------------

## 13. Reference Answer / Source Evidence Module

The system can receive a trusted reference answer directly from the
user.

When a reference answer is available, it is used for comparison with the
AI-generated response.

When a reference answer is not available, retrieved knowledge-base
evidence can provide supporting information.

The evidence sources can therefore be:

``` text
User-provided reference answer
            OR
User-provided source material
            OR
Retrieved knowledge-base evidence
```

Multiple evidence sources may also be combined.

# 14. Evaluation Orchestrator

The Evaluation Orchestrator is the central coordination component of the
evaluation pipeline.

Its responsibilities include:

-   Receive the standardized evaluation request.
-   Coordinate evidence retrieval.
-   Prepare evaluation inputs.
-   Invoke the evaluation judge agents.
-   Collect agent outputs.
-   Pass scores to the Verdict Agent.
-   Produce a structured evaluation result.

The orchestrator should not independently perform every evaluation task.

Instead, it coordinates specialized evaluation components.

### Orchestration flow

``` text
Input
  |
  v
Retrieve Evidence
  |
  v
Prepare Evaluation Context
  |
  +----------+----------+----------+
  |          |          |          |
  v          v          v          v
Relevance  Accuracy  Hallucination Completeness
  |          |          |          |
  +----------+----------+----------+
             |
             v
        Verdict Agent
             |
             v
       Final Result
```

------------------------------------------------------------------------

# 15. Relevance Judge Agent

The Relevance Judge Agent evaluates whether the AI response directly
addresses the submitted question.

### Responsibilities

-   Analyze the relationship between question and response.
-   Determine whether the response is on-topic.
-   Detect irrelevant content.
-   Evaluate whether retrieved evidence is relevant to the question.
-   Produce a relevance score.

### Input

``` text
Question
AI Response
Retrieved Evidence
```

### Output

``` text
relevance_score
relevance_label
reason
```

### Suggested scale

``` text
0 = Not relevant
1 = Slightly relevant
2 = Partially relevant
3 = Mostly relevant
4 = Highly relevant
```

The score can later be normalized to a 0--100 scale.

------------------------------------------------------------------------

# 16. Accuracy Judge Agent

The Accuracy Judge Agent evaluates factual correctness.

### Responsibilities

-   Compare the AI response with the reference answer.
-   Compare response claims with retrieved evidence.
-   Detect correct facts.
-   Detect incorrect facts.
-   Identify direct contradictions.
-   Produce an accuracy score.

### Input

``` text
Question
AI Response
Reference Answer
Retrieved Evidence
```

### Output

``` text
accuracy_score
fact_match
contradiction
reason
```

### Suggested scale

``` text
0 = Incorrect
1 = Mostly incorrect
2 = Partially correct
3 = Mostly correct
4 = Fully correct
```

------------------------------------------------------------------------

# 17. Hallucination Detection Agent

The Hallucination Detection Agent evaluates whether the response
contains unsupported or contradictory information.

### Responsibilities

-   Identify unsupported claims.
-   Compare claims with retrieved evidence.
-   Detect contradictions.
-   Identify fabricated information.
-   Determine the level of evidence support.

### Input

``` text
AI Response
Retrieved Evidence
Reference Answer
```

### Output

``` text
hallucination_score
unsupported_claims
contradiction
evidence_support
reason
```

A lower hallucination score should indicate fewer unsupported claims.

For consistency with other dimensions, the implementation can expose a
normalized hallucination-risk score and a separate support score.

------------------------------------------------------------------------

# 18. Completeness Judge Agent

The Completeness Judge Agent evaluates whether the response contains the
important information required to answer the question.

### Responsibilities

-   Identify expected answer components.
-   Compare response content with reference information.
-   Detect missing important information.
-   Determine whether the answer is complete.

### Input

``` text
Question
AI Response
Reference Answer
Retrieved Evidence
```

### Output

``` text
completeness_score
missing_information
reason
```

### Suggested scale

``` text
0 = Completely incomplete
1 = Mostly incomplete
2 = Partially complete
3 = Mostly complete
4 = Fully complete
```

------------------------------------------------------------------------

# 19. Verdict Agent

The Verdict Agent combines the outputs of the evaluation agents and
generates the final evaluation result.

### Inputs

``` text
Relevance score
Accuracy score
Hallucination assessment
Completeness score
Reference similarity
Evidence similarity
Contradiction information
Direct fact match
```

### Outputs

``` text
overall_score
verdict
summary
explanation
```

Possible verdicts:

``` text
CORRECT
PARTIALLY CORRECT
INCORRECT
UNSUPPORTED
```

The exact classification thresholds can be calibrated using benchmark
evaluation results.

------------------------------------------------------------------------

# 20. Evaluation Scoring Dimensions

The main scoring dimensions are:

  Dimension       Purpose
  --------------- ------------------------------------------------------
  Relevance       Measures whether the response addresses the question
  Accuracy        Measures factual correctness
  Hallucination   Measures unsupported or fabricated claims
  Completeness    Measures whether important information is present

Supporting signals include:

  Signal                 Purpose
  ---------------------- --------------------------------------
  Reference similarity   Similarity to trusted answer
  Evidence similarity    Similarity to retrieved evidence
  Direct fact match      Explicit expected fact detection
  Contradiction          Detection of conflicting information
  Exact match            Direct answer/evidence match
  Keyword overlap        Supporting lexical relevance
  FAISS distance         Retrieval similarity signal

------------------------------------------------------------------------

# 21. Scoring Scale

Each primary evaluation dimension can be normalized to a 0--100 scale.

Suggested interpretation:

``` text
0–24    Very Low
25–49   Low
50–74   Moderate
75–89   High
90–100  Very High
```

For the final response score, the following baseline interpretation is
proposed:

  Overall Score   Verdict
  --------------- -------------------
  75--100         Correct
  50--74          Partially Correct
  0--49           Incorrect

Strong contradiction evidence should override a high semantic similarity
score when appropriate.

Strong direct factual evidence should increase confidence in a correct
verdict.

These thresholds are configurable and should be calibrated against
benchmark examples.

------------------------------------------------------------------------

# 22. Proposed Weighted Scoring Model

A baseline weighted model can be used to combine the evaluation
dimensions.

``` text
Overall Score =
    Relevance       × 0.20
  + Accuracy        × 0.35
  + Faithfulness    × 0.20
  + Completeness    × 0.15
  + Evidence        × 0.10
```

Where each component is normalized to 0--100.

Hallucination risk can be used as a penalty:

``` text
Final Score =
    Overall Score - Hallucination Penalty
```

A direct contradiction can trigger a stronger penalty or an incorrect
verdict.

The weights are proposed for the architecture and can be changed after
benchmark calibration.

------------------------------------------------------------------------

# 23. Contradiction Handling

Contradiction is an important signal because a response can be
semantically similar to the reference while still containing an
incorrect fact.

Example:

``` text
Reference:
Paris is the capital of France.

AI Response:
Berlin is the capital of France.
```

Semantic similarity may still identify the texts as related.

However, the direct contradiction signal should identify the incorrect
city.

Therefore:

``` text
Semantic Similarity
        +
Direct Fact Check
        +
Contradiction Detection
```

should be considered together when producing the final verdict.

# 37. Design Principles

The architecture follows these principles:

### Modularity

Each evaluation responsibility is separated into a dedicated component.

### Evidence grounding

Evaluation should use reference answers and retrieved evidence whenever
available.

### Transparency

The system should expose important evaluation signals instead of
returning only a final score.

### Extensibility

Future judge agents, datasets, models, and scoring methods can be added
without redesigning the entire system.

### Reproducibility

Dataset processing, embedding generation, and indexing are implemented
as repeatable pipeline steps.

### Separation of concerns

Frontend, API, retrieval, evaluation, and scoring responsibilities are
separated.
