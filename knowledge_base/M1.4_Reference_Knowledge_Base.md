# M1.4 — Reference Knowledge Base

## 1. Purpose

The Reference Knowledge Base provides trusted reference information that can be retrieved during AI response evaluation.

It supports the evaluation system by storing benchmark questions, answers, source contexts, and processed text chunks in a searchable vector index.

The knowledge base is designed to support:

- TruthfulQA benchmark data
- SQuAD benchmark data
- Source/reference text
- Question and answer metadata
- Chunked knowledge
- Semantic embeddings
- Vector similarity search
- Evidence retrieval for response validation

## 4. Dataset Sources

### 4.1 TruthfulQA

TruthfulQA is used as a benchmark source for evaluating factual correctness and truthfulness.

Relevant information includes:

- Question
- Correct/reference answer information
- Alternative answers where available
- Benchmark metadata

The data is standardized before being added to the knowledge base.

### 4.2 SQuAD

SQuAD provides question-answer pairs grounded in source passages.

Relevant information includes:

- Question
- Answer
- Context/passage
- Source information

SQuAD is especially useful for testing retrieval and evidence-grounded evaluation.

---

## 5. Data Standardization

Before indexing, records are converted into a consistent internal representation.

A logical normalized record contains:

```json
{
  "dataset": "squad",
  "question": "What is the capital of France?",
  "answer": "Paris",
  "context": "Paris is the capital of France.",
  "source": "benchmark",
  "chunk_id": "squad_000001_000"
}
```

The exact metadata fields may vary depending on the source dataset, but the system should preserve enough information to trace retrieved evidence back to its dataset and source record.

---

## 6. Cleaning and Preprocessing

The preprocessing stage performs basic normalization before chunking.

Typical operations include:

- Removing empty records
- Removing unusable text
- Normalizing whitespace
- Standardizing field names
- Preserving question-answer relationships
- Preserving source context
- Removing unnecessary formatting

Example:

```text
Original:
"Paris   is the capital   of France."

Normalized:
"Paris is the capital of France."
```

The goal is to improve consistency without changing the meaning of the source information.

---

## 7. Chunking Strategy

Large source passages are divided into smaller chunks before embedding.

The general pipeline is:

```text
Source Context
      |
      v
Text Cleaning
      |
      v
Chunking
      |
      v
Individual Knowledge Chunks
```

Each chunk should contain enough surrounding context to remain meaningful when retrieved independently.

A chunk should also retain metadata linking it to:

- Dataset
- Question
- Answer
- Source
- Original record
- Chunk index

Example:

```json
{
  "chunk_id": "squad_000001_000",
  "dataset": "squad",
  "question": "What is the capital of France?",
  "answer": "Paris",
  "text": "Paris is the capital of France.",
  "chunk_index": 0
}
```

---

## 8. Embedding Generation

The system converts each knowledge-base chunk into a numerical vector.

The selected embedding model is:

```text
all-MiniLM-L6-v2
```

The process is:

```text
Knowledge Chunk
      |
      v
Sentence Transformer
      |
      v
Numerical Embedding Vector
```

The same embedding model is used for query embedding so that query and knowledge vectors exist in the same vector space.

---

## 9. Vector Store

FAISS is used for semantic vector search.

The indexing flow is:

```text
Chunks
  |
  v
Embeddings
  |
  v
FAISS Index
  |
  v
Saved Vector Index
```

The vector index stores the numerical representations needed for similarity search.

Metadata is stored separately so that a returned vector index position can be mapped back to the original knowledge chunk.

---

## 10. Retrieval Pipeline

When a user submits a question, the question is converted into an embedding and compared with the indexed knowledge vectors.

```text
Submitted Question
        |
        v
Query Embedding
        |
        v
FAISS Similarity Search
        |
        v
Top-K Matching Vectors
        |
        v
Metadata Lookup
        |
        v
Retrieved Evidence
```

Each retrieved result should contain information such as:

```json
{
  "text": "Paris is the capital of France.",
  "distance": 0.1,
  "index": 1,
  "dataset": "squad",
  "question": "What is the capital of France?",
  "answer": "Paris"
}
```

---

## 11. Semantic Similarity

Semantic similarity measures how closely the meaning of two pieces of text is related.

The project uses Sentence Transformers to calculate embeddings and compare them in vector space.

For evaluation, semantic similarity can be calculated between:

```text
AI Response <-> Reference Answer
```

and:

```text
AI Response <-> Retrieved Evidence
```

Higher similarity indicates stronger semantic relatedness, but similarity alone is not treated as proof of factual correctness.

This is why the validation pipeline also uses direct fact checking and contradiction detection.

---

## 12. Retrieval Quality

Retrieval quality is tested using representative questions.

For example:

```text
Question:
What is the capital of France?
```

Expected relevant evidence:

```text
Paris is the capital of France.
```

The retrieval system should rank evidence related to the submitted question above unrelated passages.

Important retrieval signals include:

- Similarity
- Vector distance
- Dataset
- Question
- Answer
- Source context
- Chunk index

## 13. Knowledge Base Integration with Evaluation

The knowledge base is not the final evaluator.

It provides evidence to the evaluation pipeline.

```text

   |                    |
   v                    |

```

---

## 14. Evidence-Based Evaluation

Retrieved evidence is used to determine whether the AI response is supported by available information.

Example:

```text
Question:
What is the capital of France?

AI Response:
Paris

Retrieved Evidence:
Paris is the capital of France.
```

This provides supporting evidence for the response.

Incorrect example:

```text
Question:
What is the capital of France?

AI Response:
London

Retrieved Evidence:
Paris is the capital of France.
```

The evidence conflicts with the AI response, providing a signal for contradiction detection.

## 18. Testing

Representative retrieval tests should verify:

### Test 1 — Relevant factual question

```text
Question:
What is the capital of France?
```

Expected:

```text
Relevant evidence about Paris and France
```

### Test 2 — Unrelated question

A question unrelated to the indexed content should not return the same evidence as the capital-of-France query.

### Test 3 — Similar wording

A differently worded question with the same meaning should retrieve semantically related evidence.

Example:

```text
Which city serves as France's capital?
```

Expected:

```text
Paris-related evidence
```

### Test 4 — Evidence metadata

Every retrieved chunk should retain enough metadata to identify its source record.

---

## 19. Limitations

The M1.4 knowledge base has several limitations:

- Semantic similarity does not guarantee factual correctness.
- Retrieval can return related but incorrect passages.
- Benchmark datasets may contain different formats and metadata.
- A fixed chunking strategy may not be optimal for every document.
- FAISS retrieval quality depends on the quality of embeddings and indexed data.
- Knowledge-base coverage depends on the available datasets and documents.

These limitations are handled in later evaluation stages through multiple evaluation agents and scoring signals.
